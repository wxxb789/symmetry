## The three jobs

All three are `continue-on-error: true` and gated `needs: changes` +
`if: needs.changes.outputs.run-heavy == 'true'` — the same gate the heavy matrix uses, so a
documentation-only pull request runs none of them and a coverage failure can never gate a pull
request (contract D14: artifacts advisory here; floors blocking at W6-10/W6-12).

| Job | `needs` | Command | Artifact | Report path |
| --- | --- | --- | --- | --- |
| `coverage-control` | `[changes, contracts]` | `mix test --cover` | `control-coverage` | `control/cover/` |
| `coverage-daemon` | `[changes]` | `go test -count=1 -timeout 1200s -coverprofile=coverage.out ./...` under the stdio-only boundary; `go test` sets `GOCOVERDIR` for each instrumented test binary itself, and the helper environment builder forwards it (residual risks) | `daemon-coverage` | `daemon/coverage.out` |
| `coverage-frontend` | `[changes]` | `pnpm --filter @symmetry/frontend exec vitest run --coverage` | `frontend-coverage` | `frontend/coverage/` |

Each report path is the path the root `.gitignore` already reserves (`/control/cover/` `:46`,
`/daemon/coverage.out` `:55`, `/frontend/coverage/` `:80` at the base revision), so the plane needs
no ignore-rule change and no generated bytes can leak into a commit.

Placement: the three jobs are one contiguous block directly after the `control` job, so the diff is
entirely additive and no pre-existing job body is re-indented or reordered. The order inside the
block is the order of the deliverable table.

### Why separate jobs, and what each one mirrors

- **Separate jobs are the P1-1 amendment.** The review refused `-coverprofile` on the existing race
  step (it sits at `-timeout 600s`, and `internal/app` alone measured ~386 s of the ~449 s step) and
  refused a coverage step inside the `control` job's `mix test` shape (`mix test --cover` under the
  default 90 % summary threshold fails a below-floor report — the review measured exit 1, this
  toolchain measured exit 3 in the mutation row below — and the existing `mix test` step is the
  canonical suite). A separate job keeps every pre-existing step byte-identical and gives the new
  work its own runner, its own timeout and its own `continue-on-error` conclusion.
- **`coverage-control` mirrors the `control` job's prerequisites**: the `postgres:18.6-alpine`
  service and the `POSTGRES_*` env block (the suite needs a database and the `test` alias creates
  and migrates it), `erlef/setup-beam` at Elixir 1.20.4/OTP 29.0.6, and the `portal-assets`
  artifact staged into `control/priv/static/portal/` — four `:portal_assets` cases in
  `PortalControllerTest` assert against the real staged bundle
  (`control/test/support/portal_bundle.ex:1-24`), which is why the job needs `contracts` beside
  `changes`. `needs:` still contains `changes`, the gate the classifier suite checks.
- **`coverage-daemon` mirrors the daemon job's two behavioural prerequisites**: the pinned Go
  toolchain (`setup-go` 1.27.0, `cache-dependency-path: daemon/go.sum`) and
  `scripts/ci/prepare-private-namespace-tests.sh` (the suite's private user/PID namespace fixtures
  need the prepared private `unshare` path), and it runs the tests through
  `scripts/ci/stdio-only-caller-boundary.py`, the single implementation of the descriptor boundary
  the daemon job establishes before Go. `go test` sets `GOCOVERDIR` for each instrumented test
  binary itself (`cmd/go` `test.go` appends it beside `-test.gocoverdir`), and `internal/execution`'s
  helper environment builder (`minimalEnvironment()` in `runner_test.go`) forwards it to the
  re-exec'd helper children, so an instrumented child writes covdata instead of printing the
  coverage runtime's "GOCOVERDIR not set" warning (run `44887419717`; residual risks below) — no
  package is excluded from the profile and the step carries no env of its own. The `-timeout` is
  this step's own budget
  (1200 s, twice the default 600 s) because coverage instrumentation slows every package; the race
  step keeps its `-timeout 600s` untouched.
- **`coverage-frontend` mirrors the `contracts` job's frontend toolchain**: `pnpm/action-setup` at
  12.17.0, `actions/setup-node` at Node 24 with `cache: pnpm`, then `pnpm install --frozen-lockfile`
  at the workspace root. `pnpm --filter @symmetry/frontend exec vitest run --coverage` runs vitest
  in the package directory, which is where `reportsDirectory: "coverage"` resolves.

## `control/mix.exs` — why `threshold: 0` is the whole fix

`mix test --cover` runs the project's coverage tool through `Mix.Tasks.Test.Coverage`, whose
`get_threshold/1` is `Keyword.get(opts, :threshold, @default_threshold)` with
`@default_threshold 90` (`mix/lib/mix/tasks/test.coverage.ex:143,:409-410` in the portable
toolchain). The default `test_coverage` map is `[output: "cover", tool: Mix.Tasks.Test.Coverage]`
(`mix/lib/mix/tasks/test.ex:524`), so without the key the summary compares against 90 and
`print_failed_threshold/2` installs `System.at_exit(fn _ -> exit({:shutdown, 3}) end)`
(`test.coverage.ex:316-317,:379-383`); the review measured that path as exit 1, and this toolchain
measured exit 3 in the mutation row below. `summary: [threshold: 0]` makes `totals < 0` false for
every report, so the step's status
is the suite's own: the artifact is advisory by construction, and flipping a floor back on later
(W6-10/W6-12) is a one-line change in the same key. `summary: false` would have removed the
per-module table from the job log as well, which is the number a burn-down slice reads; the
threshold form keeps it.

## The classifier suite: what the existing model already covers, and what the added jobs need

`check_job_gating` (the suite's job model) refuses an unconditional job, requires every gated job to
name `changes` in `needs:`, and requires its `if:` to be exactly
`needs.changes.outputs.<pinned-or-default> == 'true'`. The three coverage jobs satisfy it as
written: they are conditional, they need `changes`, and they gate on the default output
(`run-heavy`). What the suite did not have is a pin that names the added jobs: without one, a later
edit could re-gate a coverage job on another output and still fail — but only through the generic
message. This change adds:

- `COVERAGE_JOBS`, the three job names, and `check_coverage_plane_routing(model, outputs)`: each
  job must exist, and for every fixture diff it must run exactly when that diff's `run-heavy` is
  true. The check derives the "ran" set from the workflow's own `needs:`/`if:` text through
  `ran_jobs`, so it measures the pinned routing, not a second copy of it.
- `check_coverage_jobs_are_advisory(workflow_text)`: each coverage job's own block must carry the
  job-level `continue-on-error: true` line, so dropping the advisory flag — the contract's
  "a coverage job without `continue-on-error` = not achieved" failure mode — reddens the suite
  instead of waiting for review.
- `check_coverage_artifacts(workflow_text)`: each coverage job's own block must carry its pinned
  upload step (`if: always()` on `actions/upload-artifact@v4` with the pinned artifact name and
  report path), the command line(s) that produce the report, and — for `coverage-control` and
  `coverage-daemon` — the `defaults.run.working-directory` the command and the report path
  resolve against, so a deleted upload step, a dropped always-upload, a renamed artifact, a
  moved path, a dropped command or a strayed working directory reddens locally instead of only
  in the draft-PR run.
- `test_the_coverage_jobs_follow_the_heavy_matrix_across_every_fixture`, which runs the routing
  and advisory checks against all 16 fixture diffs and the artifact pin against the workflow
  text (the fixtures are the added jobs' routing evidence: a docs-only fixture must run none of
  them, a code fixture must run all three).
- `test_mutation_regating_a_coverage_job_off_the_heavy_output_breaks_its_routing`,
  `test_mutation_dropping_a_coverage_jobs_advisory_flag_breaks_the_advisory_check`,
  `test_mutation_dropping_a_coverage_uploads_always_flag_breaks_the_artifact_check` and
  `test_mutation_dropping_a_coverage_jobs_working_directory_breaks_the_artifact_check`, which
  re-gate `coverage-daemon` on `run-citations`, strip its advisory line, strip its upload's
  `if: always()` and delete its `defaults.run` block in in-memory copies, asserting the matching
  check reddens — the suite's own style of proving an assertion is not vacuous.

No pre-existing assertion is weakened, renamed or deleted; the added pins are additive and use the
suite's existing parsers (`job_blocks`, `parse_model`, `ran_jobs`, `require`). Review round 2
removed the case that pinned the step-level `GOCOVERDIR` env: `go test` overrides that variable for
the test binary, so the pin guarded dead config, not the helper forwarding.

## Decisions and their justification

1. **One contiguous block, three jobs, no matrices.** A matrix would have to express three
   different toolchains, artifact paths and prerequisite sets; three explicit jobs match the file's
   existing style and keep each job's prerequisites readable next to its command.
2. **Stable artifact names** (`control-coverage`, `daemon-coverage`, `frontend-coverage`) with
   `retention-days: 7` and `if-no-files-found: warn`, matching the repository's test-report
   artifact (`workspace-render`, also a report artifact with `warn`). A rerun attempt re-uploads
   under the same name; the evidence artifact pattern that carries `run_id`/`run_attempt` exists for
   artifacts whose *absence must fail* (OpenCode provenance, the Pi E2E logs) — a missing
   coverage report is not a gate here, it is a red advisory step in the log.
3. **`-timeout 1200s` on the daemon coverage step, `timeout-minutes` on every coverage job.** The
   race step's 600 s budget is a pre-existing property this slice must not touch; the coverage job
   declares its own doubled per-package budget and a job bound (30/60/30 minutes), so a hung run
   cannot consume a runner for hours.
4. **`needs: [changes, contracts]` for `coverage-control`.** The four `:portal_assets` cases need
   the staged bundle; building it inside the coverage job would duplicate the `contracts` job's
   build and change which bytes are asserted against. `changes` remains in `needs:` and the gate is
   unchanged.
5. **`pnpm --filter @symmetry/frontend exec vitest run --coverage` rather than a new
   `test:coverage` script.** `frontend/package.json` is outside the owned set, and `exec` composes
   the existing `test` script without editing it.
6. **The coverage pin lives in the classifier suite, not in a new test file.** The suite already
   owns the job-routing model and its fixtures; a second file would need the same extraction
   machinery and would drift.
7. **No `if: always()` on the coverage steps themselves.** The report is the step's own output; if
   an earlier step of the same job fails there is nothing to report, and `always()` on a coverage
   step could only manufacture a report from a half-configured job. The upload step does carry
   `if: always()`, so a failing coverage run still uploads whatever it produced.

  `TestRunBoundedCommandStopsDescendantHoldingOutputPipe`,
  `TestRunBoundedCommandDoesNotInstallDurableCallbacks`,
  `TestStartDrainsStdoutAndStderrBeyondSixtyFourKiB` — which assert the helper child's exact output

  Review round 1 excluded the package; the contract's review-round-1 Conductor decision (2026-11-21)
  rejected that and ratified the helper-environment fix: with coverage on, `go test` passes
  `-test.gocoverdir=<objdir>/gocoverdir` and appends `GOCOVERDIR=<objdir>/gocoverdir` to the
  instrumented test binary's environment (`cmd/go` `test.go`), and `minimalEnvironment()` forwards
  that value to the re-exec'd helper children, so an instrumented child writes covdata into the
  tool's merge directory instead of warning and no package leaves the profile. The step carries no
  `GOCOVERDIR` env of its own: the tool's appended value is the environment's last occurrence and
  Go's environment deduplication keeps the last value, so a step-level value never reaches the test
  binary (review round 2 deleted the env and its `mkdir` as the no-ops they were). The four
  assertions are unchanged, and the forwarded variable is the only helper-environment difference
  (it is unset in ordinary runs, so the child environment stays minimal there). Concurrent
  instrumented children share the tool's merge directory; on Windows the coverage runtime's covmeta
  rename can then fail (`Access is denied` — on Linux the rename replaces atomically), so the
  round-2 local runs serialize or drive the test binary directly, and the hosted Linux re-run is
  the oracle for the job's conclusion.
